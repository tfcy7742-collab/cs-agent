# 长会话客服 Agent

> 电商售后场景的客服 Agent：**能陪用户聊几十上百轮、跨会话记住人、该查库就查库、该转人工就转人工、绝不编造订单与政策**。

当前进度：**P1–P7 全部完成**（会话循环 / 持久化 / SSE / 分层记忆 / 事实版本化 / 跨会话画像 /
结构化会话状态 / 六个技能工具 + 政策检索 / 转人工兜底 / 评测与可观测 / React 界面与人工工作台）。

> ⚠️ **数据来源声明**：订单、物流、退款数据与政策条文都是**为演示编写的本地模拟数据**，
> 不是任何真实电商系统或平台的对接结果。每个工具的返回值里都带 ``data_source`` 标注，
> 接口与提示词里也会带上"演示数据"字样。

---

## 一、它要解决什么问题

普通 Agent demo 的会话是"一问一答式"的工具调用；客服场景的真正难点在**跨轮次的状态与记忆**：

| 难点 | 具体表现 | 普通做法为什么挂 |
| --- | --- | --- |
| 上下文无限增长 | 用户聊到第 80 轮，历史几万 token | 要么爆窗口，要么粗暴截断——一截断第 3 轮给的订单号就没了 |
| 信息在轮次间丢失 | 第 5 轮"帮我查订单"，第 12 轮"那这个能退吗" | "这个"指代什么？没有结构化状态只能靠模型猜 |
| 重复追问 | 已经说过收货地址，第 6 轮又问一遍 | 长会话里最伤体验的失败 |
| 该转人工不转 | 用户已经说了三遍"我要投诉" | 纯靠模型判断不稳定，需要可量化的触发规则 |

## 二、架构主线

### 2.1 分层记忆（长会话的解法）

```
┌─────────────────────────────────────────────────────────┐
│ L1 工作记忆（进本轮 prompt）                              │
│   最近 N 轮原文 + 滚动摘要 + 会话状态卡 + 用户画像片段      │
├─────────────────────────────────────────────────────────┤
│ L2 会话状态（结构化，不塞全文）                            │
│   槽位：订单号 / 用户身份 / 诉求类型 / 已确认参数           │
│   待办：多意图拆解后的任务栈（未完成的不丢）                │
│   未决：待用户补充的信息（驱动下一轮追问）                  │
├─────────────────────────────────────────────────────────┤
│ L3 用户画像（跨会话，长期）                                │
│   已确认的稳定信息 + 历史工单摘要                          │
└─────────────────────────────────────────────────────────┘
```

三个关键机制：

* **滚动摘要 + 最近原文**：超阈值就把最早一段压成摘要，但**结构化事实单独存**——摘要会丢细节，订单号绝不能只活在摘要里；
* **事实版本化**：用户改地址后新值**覆盖**旧值而不是并列（并列会让模型随机挑一个，这是长会话里最隐蔽的 bug）；
* **工具结果按需重放**：订单详情这类大 JSON 不常驻上下文，只存"已查过订单 X"的指针，需要时重放。

> **P2 已把三层全部落地**：滚动摘要、版本化事实、跨会话画像都已实现并接入每轮对话
> （见 2.4）。P1 时期预留的 `summary / state / profile` 通道现在填的是真实内容。

### 2.3 一轮对话的流程

```
用户消息
  │
  ├─ 1. 先落库（模型失败也不能丢用户的话）
  ├─ 2. 抽取事实：正则先行（确定性、不幻觉）+ LLM 补漏 → 并入会话事实（值变化保留旧值）
  ├─ 3. 超阈值就滚动压缩：把最老的原文折进摘要，并标记原文已覆盖
  ├─ 4. 组装工作记忆：最近 N 轮原文 + 摘要 + 事实 + 画像
  ├─ 5. 流式调用模型，边产出边推送
  └─ 6. 落库助手消息 + 更新轮次 + 记录轨迹（含记忆指标）
```

### 2.4 分层记忆的实现细节（P2）

**触发压缩的条件**（任一满足）：未压缩原文条数 > 工作窗口 ×2，或未压缩原文总字符数 > `HISTORY_COMPRESS_CHARS`。

**摘要怎么做**（这是最容易做歪的地方）：

| 步骤 | 做法 | 为什么 |
| --- | --- | --- |
| 生成 | 模型按固定四段式输出：用户身份 / 已确认信息 / 诉求与进展 / 待办未决 | 结构固定才不会漏掉"未决事项" |
| 预算 | `min(被折叠原文 × 0.4, 历史阈值 × 0.5)`，下限 400 字 | 预算太小（实测 120）模型必然超标，只能一路退化 |
| 超标 | 让模型**改写自己**（二次压缩），而不是丢掉 LLM 摘要 | 一超标就退回抽取式，摘要质量会反复掉档 |
| 兜底 | 不可用时退化为**抽取式**，并明确标注"抽取式" | 宁可长一点，也不能凭空编造；且如实标注来源 |
| 防递归 | 抽取式只继承旧摘要的"要点"段，且总长受预算限制 | 整段复制旧摘要会让摘要**指数膨胀**（实测踩过） |
| 原文 | **标记覆盖，不删除** | 排查问题、用户改口回溯都要靠原文 |

**摘要与事实是两条独立通道**：摘要会有损，所以订单号这类关键事实**结构化单独存**。
实测第 1 轮给出的订单号，在第 26 轮仍出现在提示里——它靠的是事实通道，不是摘要。

**事实版本化**：`{"value": 新值, "previous": 旧值, "changed_at": ..., "source": regex|llm}`。
新值覆盖、旧值留痕，渲染进提示时写成 `上海（此前为 北京）`——
既避免"新旧并列让模型随机挑一个"，也避免"改口后旧值彻底丢失"。

**跨会话白名单**：只有 `称呼 / 城市 / 联系方式 / 会员等级 / 沟通偏好 / 常用收货地址`
会沉淀进用户画像；`订单号 / 诉求 / 退货原因` 属于单会话信息，**绝不跨会话**——
否则用户开新会话问"我的订单状态"，模型会拿上一单的订单号去查。

### 2.6 结构化会话状态（P3）

记忆回答"我知道什么"，状态回答"我正在办什么事、还缺什么"。两者分开存：

```
session_state['facts']  ← 版本化事实（跨任务共享的知识）
session_state['tasks']  ← 待办栈
session_state['slots']  ← 槽位库（已知参数，跨任务共享）
session_state['asked_slots'] ← 已经问过什么（防重复追问）
```

**任务表**（`tasks.py`，单一事实来源）

| 任务 | 硬槽位（缺了必须问） | 软槽位（缺了照样办） |
| --- | --- | --- |
| 查询物流 / 查询订单 / 退款进度 / 开具发票 | 订单号 | 商品名称、发票抬头 |
| 退货 / 换货 | 订单号 | 退货原因、商品名称 |
| 修改收货地址 | 订单号、新地址 | — |
| 转人工工单 | 问题描述 | — |

硬槽位与软槽位的分界就是体验的分界：**绝不能因为缺软槽位就拦着用户**。
"退货运费谁承担"这种问题本身不依赖具体订单，被要订单号是最烦人的失败。

**待办栈**：多意图（「我要退货，另外查下物流」）两件事都进栈，
第一件办完自动激活下一件；同 kind 不重复建（避免待办列表变垃圾场）；
用户说"算了"就真的出栈，而不是假装完成。

**追问策略**（三点，都是踩过坑才定下来的）

1. 硬槽位缺 → 问一次，**一次只问最靠前的那一个**（订单号永远优先）；
2. 问过一次还缺 → 不再重复，改为按政策作答（用户可以只想知道规则）；
3. **规则咨询不索要单号**：判据是"问句信号 **且** 无动作词 **且** 无指代词"。
   这条是线上实测补的——用户问"退货运费一般谁承担？"，意图抽取把"退货"也抽了出来，
   系统就去要订单号，等于用规则问题把用户拦在门外。

**指代消解**：`"那这个能退吗"` 里的"这个"必须绑定到具体订单；
绑不唯一时**澄清**而不是猜——猜错会直接办错单子，是客服场景里代价最高的错误。
用户改过单号后，`previous` 里的旧单号**不会**被当成"这一单"。

### 2.7 技能层：六个工具与"不编造"的落地（P4）

| 工具 | 能力 | 治理标记 |
| --- | --- | --- |
| `query_order` | 订单详情（商品/金额/状态/收货信息） | 只读、可重试 |
| `track_logistics` | 物流轨迹与预计送达 | 只读、可重试 |
| `check_returnable` | 判断能否退货，**给出依据条款** | 只读、可重试 |
| `query_refund` | 退款进度与到账时效 | 只读、可重试 |
| `search_policy` | 检索平台政策 | 只读、可重试 |
| `submit_return_request` | 提交退货申请 | **有副作用：必须用户确认、不重试** |

**工具协议**（`tools/base.py`）：每个工具声明名称、说明、参数 JSON Schema、超时、成本档位、
是否可重试、是否需要人工确认。超时/重试/参数校验/确认标记都在基类统一实现——
新增工具自动获得同样的保护。

**三层防"编造"**（这是 P4 的核心价值）：

```
第一层：没参数不空调用  → 缺订单号时先追问（P3 的状态机接管）
第二层：工具如实返回    → 订单不存在就 not_found，检索不到就返回空，绝不凑数
第三层：提示词钉死事实  → 工具结果进系统提示，并明确写「唯一事实来源，禁止编造」
```

线上实测（`scripts/check_tools_online.py`，真实模型）：

| 场景 | 结果 |
| --- | --- |
| 查物流 | 回复里出现工具返回的真实运单号 `SF1234567890123` 与承运商"顺丰速运" |
| 订单号不存在 | 回复"系统没有查询到这个订单，麻烦核对订单号"，**未编造**任何物流信息 |
| 问退货运费 | 按政策原文分商家责任/个人原因作答 |
| 申请退货 | 先请确认并说明"不可撤销"；**确认前订单状态不变**；确认后才执行并如实回报金额与时效 |

**政策检索的实现与局限**：中文二元组 + IDF 打分（零依赖、可离线、结果确定），
命中会返回条款原文、来源与命中词，便于核对。
局限很明确——**同义改写召回不了**（"运费谁出"能命中，"这笔钱谁掏"可能命不中），
这一点在 README 里如实写明，不装作是语义检索。

### 2.8 人工兜底：可量化的转人工规则（P5）

**不让模型决定"要不要转人工"**——那样不稳定（同诉求两次结果可能不同）、不可测、
也无法解释。判定放在规则层，每条规则有名字、权重与可读理由，进轨迹可追溯；
模型只负责"把转接这件事说清楚"。

| 规则 | 触发条件 | 处理 |
| --- | --- | --- |
| `explicit_request` | 明确要求转人工 / 找主管 | 立即转 |
| `out_of_scope` | 赔偿、免运费、加急、额外优惠、投诉升级、改金额 | 立即转（**不能自己答应**） |
| `negative_sentiment` | 情绪词典累计打分 ≥ 5 | 阈值转 |
| `repeat_unresolved` | 同一诉求反复提及且期间无成功工具结果 | 阈值转 |
| `answer_loop` | 连续 2 轮重复同一诉求且始终无工具佐证 | 阈值转 |

**推迟策略**：分数够了但本轮刚向用户提过问（正在等补充信息）时先不打断，
记 `defer` 并留待下一轮——避免"用户正准备回答，却被转走了"。

**交接单**（结构化，不让坐席从零开始）：
诉求 / 已核实信息 / 未办结事项（含仍缺哪些信息）/ 系统已尝试 / 当前卡点 / 触发规则 /
用户情绪 / 历史摘要。示例：

```
【交接单 HOD73AAC6171】
用户：ho-1｜轮次：1
已核实信息：订单号=SO20260101；诉求=转人工
未办结事项：转人工工单（active）仍缺：咨询内容
当前卡点：用户明确要求转人工
用户情绪：4 分（一直没、仍未解决）
```

**挂起与接续**（长会话里最容易做漏的两点）：

* **挂起持久化**：会话状态与工单都落库，服务重启后坐席仍能接手（有专门的恢复测试）；
* **接续不重跑**：坐席回复后只追加一条消息，会话回到 active，**槽位与事实原样保留**——
  用户不会被再问一遍订单号；人工消息以 `[人工客服]` 标记进入上下文，
  模型既不会把它当成自己说的，也不会重复人工已答复的内容；
* **人工消息永不压缩**：它是权威信息（承诺了什么、怎么处理的），被摘要糊掉会让后续对话失去依据。

线上实测（`scripts/check_handoff_online.py`，真实模型）：工单号如实给出、
转接原因说清（"超出我的处理权限，需由人工专员核实"）、**未出现任何越权承诺**、
纯咨询不转人工、接续后不再追问订单号。

### 2.9 评测与可观测（P6）

**离线与在线测的不是一回事**——报告里第一行就写明模式，绝不混着报：

| 模式 | 能测什么 | 不能测什么 |
| --- | --- | --- |
| **offline**（默认，CI 可用） | 工具路由、槽位填充、追问策略、转人工判定、写操作确认、注入场景的副作用、提示词里是否带上"禁止编造" | **回答质量**（模型是模板应答） |
| **online**（真实模型） | 回答是否引用工具真实数据、查不到是否如实说、是否越权承诺、是否重复追问 | — |

**18 个场景**（`eval_scenarios.py`），三类：

* **业务 11 个**：查物流（有/无单号）、订单不存在、政策问答（命中/不命中）、
  退货资格、写操作确认、超权限转人工、明确转人工、多意图待办、咨询不被索要订单号；
* **长会话 1 个**：关键信息前置 + N 轮闲聊，断言订单号与称呼仍在上下文里，
  且确实触发过压缩（否则这个场景没测到东西）；
* **注入对抗 6 个**：要求泄露提示词、伪造管理员改金额、冒充人工承诺赔偿、
  要求无视政策赔偿——**硬不变量是"订单数据一个字都不能变"**，
  比"看模型有没有被说服"可靠得多（副作用是客观事实）。

**指标口径**（写死在 `evaluation.compute_metrics`，避免"指标好看但含义随人解释"）：

```
任务完成率  只在"有明确业务目标"的场景上算（对抗场景没有业务目标，
            算进分母会让指标失去意义——第一版就是这么错的）
转人工准确率 规则层是确定性的，这项应恒为 1.0，掉下来就说明规则被改坏了
重复追问率  出现追问的场景里，同一槽位被问 ≥2 次的比例
对抗通过率  注入场景全部断言通过的比例
```

**实测结果**（`scripts/run_eval.py`）：

| 模式 | 场景 | 通过率 | 任务完成率 | 转人工准确率 | 重复追问率 | 对抗通过率 |
| --- | --- | --- | --- | --- | --- | --- |
| offline（24 轮长会话） | 18 | 100% | 100% | 100% | 0% | 100% |
| online（真实模型，8 轮） | 18 | 100% | 100% | 100% | 0% | 100% |

**逐轮轨迹**（`GET /api/sessions/{id}/traces`）：每轮的决策动作、调用的工具、
命中的转人工规则、记忆是否压缩与压缩比、prompt/completion token、首字与总延迟——
长会话出问题时靠它定位"哪一轮开始重复追问、哪一轮压缩了上下文"。

### 2.10 SSE 事件协议

| 事件 | 载荷 | 说明 |
| --- | --- | --- |
| `session` | `session_id` / `turn` / `created` / `title` | 会话确认（前端拿到 ID） |
| `start` | `history_messages` / `prompt_chars` / `prompt_token_estimate` / `compressed` / `offline` / `model` / `memory` / `plan` / `state` / `tools` / `escalation` / `handoff` / `system_prompt` / `messages` | 本轮的工作记忆规模、记忆操作、行动计划、工具调用、转人工判定与工单，以及**真正发给模型的完整上下文**（`system_prompt` 是 system 部分，`messages` 含人工坐席消息与历史原文） |
| `delta` | `text` | 增量文本 |
| `done` | `content` / `latency_ms` / `first_token_ms` / `usage` / `trace` / `error` | 收尾与用量（`error` 非空表示本轮部分失败） |
| `error` | `message` / `retryable` | 执行失败 |

> **用量口径**：流式响应里供应商通常不回传 `usage`，因此
> `prompt_tokens` / `completion_tokens` 是**按内容估算**的（中文 1 字≈1 token，
> 英文 4 字符≈1 token），只用于观察上下文增长趋势，**不能用于计费口径**。

> 一个帧以**空行**结束，`event:` 与 `data:` 各占一行。
> 解析时必须按帧累积（见 `tests/test_p1_api.py` 的 `parse_sse`），
> 否则载荷里的换行会把消息截断——这个坑实测踩过。

## 三、快速开始

```bash
cd cs-agent
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

copy .env.example .env      # 然后按需填 DEEPSEEK_API_KEY
.venv\Scripts\python.exe -m cs_agent.main
```

服务默认在 `http://127.0.0.1:8001`，接口文档 `/docs`。

**没有 Key 也能跑**：`LLM_MODE=auto` 且未配置 Key 时进入**离线模板模式**，
接口、SSE 协议、持久化行为完全一致，只有应答改为本地模板（并如实标注"离线模式"，不假装是模型）。

## 四、界面（P7）

React + TypeScript + Vite，**无组件库**（167 KB 打包，比带 UI 框架小一个数量级）。
构建产物由后端挂在 `/ui` 下提供，**不需要单独起前端服务**。

```bash
cd frontend
npm install
npm run build        # 产物 frontend/dist，后端启动时自动挂载到 /ui
```

然后打开 **http://127.0.0.1:8001/ui/**。

三个视图：

| 视图 | 做什么 |
| --- | --- |
| **对话** | 左侧会话列表、中间 SSE 流式对话、右侧**检视面板** |
| **人工工作台** | 工单队列 + 交接单 + 认领/回复/办结（回复后用户会话自动恢复） |
| **评测** | 一键跑离线评测集，展示六项指标与失败断言 |

**右侧检视面板**是这个项目最值得看的地方——把 Agent 的内部状态直接摊开：

* **本轮决策**：计划动作（追问/回答）、识别到的意图、调用了哪个工具、结果如何、
  是否有待确认的写操作、**转人工判定与命中的规则**；
* **状态**：槽位（已知信息）、待办栈（哪个在办、哪些排队、还缺什么）、已追问过的槽位；
* **记忆**：本轮抽到的事实与改口记录、历史 vs 工作记忆字符数、压缩比、**滚动摘要全文**；
* **轨迹**：逐轮的 tokens、耗时、工具与动作——长会话出问题靠它定位。

> 前端调用统一用**站点绝对路径** `/api/...`：界面挂在 `/ui` 下，相对路径会被解析成
> `/ui/api/...` 而 404（这个坑在挂载时踩过，已在 `api.ts` 里写明）。
> SPA 深链接（`/ui/workspace`）由后端的 `SPAStaticFiles` 回退到 `index.html`，
> 否则刷新页面就 404。

## 五、接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/health` | 健康检查（模型模式、Key 脱敏、存储、会话参数） |
| `POST` | `/api/sessions` | 新建会话 |

| `GET` | `/api/sessions/{id}` | 会话详情 + 消息历史 + 统计 |
| `GET` | `/api/sessions/{id}/memory` | 记忆体检：分层规模、压缩比、事实、画像、摘要全文 |
| `GET` | `/api/sessions/{id}/state` | 结构化状态：待办栈、槽位、还缺哪些信息 |
| `GET` | `/api/handoffs` | 坐席工作台：工单列表（等待中排最前） |
| `GET` | `/api/handoffs/{id}` | 工单详情：交接单文本 + 会话消息 + 结构化状态 |
| `POST` | `/api/handoffs/{id}/accept` | 坐席认领 |
| `POST` | `/api/handoffs/{id}/reply` | 坐席回复（写入会话并恢复活跃态） |
| `POST` | `/api/handoffs/{id}/resolve` | 办结工单 |
| `POST` | `/api/sessions/{id}/compact` | 手动触发一次滚动压缩（调试/演示用） |
| `GET` | `/api/sessions/{id}/traces` | 逐轮轨迹：决策/工具/转人工/记忆/用量/延迟 |
| `GET` | `/api/eval/scenarios` | 评测场景清单（覆盖方向与轮次） |
| `POST` | `/api/eval/run` | 跑一次离线评测并返回指标与可读报告 |

```bash

  -H "Content-Type: application/json" \
```

## 七、关键设计取舍

**1. 为什么不用 openai SDK / LangChain**
本项目对模型的需求很窄（一次补全 + 流式增量），用标准库 `urllib` 直接打 HTTP
能把依赖压到 `fastapi + uvicorn`，也便于把超时、重试、错误分类这些真正要讲清楚的地方
写明白，而不是埋进框架里。

**2. 为什么流式失败只在"还没吐字"时重试**
已经产出部分文本后再重试，用户会看到重复内容。所以：未产出可重试，已产出直接抛错让上层收尾。
并且**已产出的部分仍会落库**（标记 `partial`），保证"用户看到的"与"历史记录的"一致。

**3. 为什么先落库再调模型**
模型调用失败不能丢用户的话。测试 `test_user_message_is_persisted_even_if_model_fails`
专门盯这条。

**4. 为什么非流式与流式走同一条生成器**
`chat_once` 消费同一个 SSE 生成器，从根上避免"流式与非流式行为不一致"这类经典问题。

**5. 为什么 SQLite 用线程本地连接**
FastAPI 在线程池里跑同步逻辑，SQLite 默认 `check_same_thread` 会直接报错；
线程本地连接 + WAL + 写锁是最简单且不会踩坑的做法。

## 八、诚实的局限

* 订单、物流、库存、退款进度**全是本地模拟数据**，不是真实电商系统对接；
  政策条文同样是为演示编写的示例文本（每个工具返回值都带 `data_source` 标注）；
* **政策检索是关键词 + 二元组，不是语义检索**：同义改写可能召不回来
  （"运费谁出"能中，"这笔钱谁掏"可能不中）；检索不到时返回空并如实告知，
  而不是拿一条不相关的条款凑数；
* 工具意图路由基于**关键词 + 少量规则**（`INTENT_TOOLS`），不是训练出来的分类器；
* **规则类问题现在会先查政策库**：由此带来的后果是"能查到就按原文答、
  查不到就说没查到"——可能不如大模型自由发挥流畅，但不会有编造风险；
* 长会话的摘要压缩**必然有损**：接口与报告里给的是实测 `compression_ratio`，
  而不是宣称无损。实测 26 轮会话压缩比约 0.12；
* 事实抽取的**正则部分**可能漏抽（宁可漏，不可错），LLM 部分依赖模型质量，
  每条事实都带 `source`（regex / llm）可追溯是谁抽的；
* 情绪识别是**词典 + 规则近似**（`handoff_rules.NEGATIVE_WORDS`），不是独立情感模型：
  表达方式变化大时可能漏判；阈值与词典都可通过 `EscalationThresholds` 调整，
  实测"怎么这么慢，都几天了"得 4 分、"我要投诉"得 3 分；
* 转人工规则里的**超权限清单是枚举式**的（赔偿/免运费/加急/额外优惠/改金额/投诉升级），
  没枚举到的越权诉求不会被拦——这是刻意取舍（宁可漏拦，也不要把正常请求都转人工）；
* 人工工作台是**模拟的**（接口 + 数据），不做真实坐席系统集成——它是"把闭环演示完整"的界面，不是可上线的坐席系统；
* **评测集的规模有限**：18 个场景覆盖的是关键路径，不是统计意义上的充分样本；
  离线评测不能替代在线验收（两者测的东西不同，报告里已分别标注）；
* 前端只覆盖**单用户视角**：没有登录、没有多坐席并发抢单、没有工单分配策略。
